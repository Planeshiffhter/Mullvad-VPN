## Status and scope rules

Each feature row has exactly one status and one scope. Local unit success cannot promote essential unexecuted browser/OS behavior to tested support. `BLOCKED` records a concrete external acceptance prerequisite; it is not a synonym for unfinished coding. Optional/future scope is independent of status.

| Status | Meaning |
| --- | --- |
| `IMPLEMENTED_TESTED` | Relevant code and behavioral evidence passed for the bounded behavior stated; no broader runtime claim follows. |
| `IMPLEMENTED_UNVERIFIED` | Code exists, but essential real browser/platform/service acceptance for this claim is unexecuted. |
| `PARTIAL` | Some required behavior exists, but material implementation or acceptance is incomplete. |
| `SOURCE_ONLY` | Matching third-party code is preserved; no independent integration/build/device verification is established. |
| `DOCUMENTED_ONLY` | Plans/specifications/configuration examples or runbooks exist without the claimed operational implementation. |
| `NOT_IMPLEMENTED` | No corresponding original-product implementation was found in the audited tree. Contextual source/plan links are not implementation evidence. |
| `BLOCKED` | A stated external prerequisite prevents the selected work/acceptance, such as permitted browser, authorized endpoint, host or device. |

**Scopes:** `CORE` = initial browser/Linux VPN product requirement; `SUPPORTING` = development/operations infrastructure; `OPTIONAL` = enhancement beyond MVP; `FUTURE` = deliberately later platform/customer/fleet expansion. Android, Windows, macOS and Firefox are explicit requested destinations, classified FUTURE rather than dismissed as optional. Priorities P0–P3 express the dependency-ordered roadmap, not current status or an estimated delivery date.

### Reproduced defect versus untested risks

**T24 remains unresolved and is now reproduced as a UI defect.** A fresh in-memory Store with a 1,024-byte account quota issued a real control-API grant; usage was set to quota. The real TLS API returned `state: exhausted`, `active: false`; `Store.authorize` rejected that grant. The unchanged operations page, loaded in real Chromium, displayed `1` active grant and `Authorized` because it uses revocation/expiry only. Its existing website test fixture omits the state fields.

The diagnostic used a temporary loopback HTTP page/bridge that forwarded API calls to the real TLS control API with explicit CA verification. This exercises actual UI and server state, but is **not** production-browser TLS, extension routing or a live exit. It printed no credentials, used temporary fixture state, and closed its browser/listeners/store. No app code or committed regression changed. T24 must add a durable failing-before/passing-after regression and fix authoritative state/count rendering without changing server enforcement.

The earlier occupied-port startup-cleanup error is **verified fixed**, with existing regressions passing again in V2; it is not an open defect. DNS/WebRTC/IPv6 leakage, native privilege/key security, production certificate renewal and deployed recovery remain missing acceptance or risks, not demonstrated exploits. Do not infer a server authorization bypass from the reproduced dashboard display error.
## Current Product Direction

The intended product is an independent, secure, multi-platform VPN with Chrome/Chromium and Firefox extensions, Linux/Windows/macOS desktop clients, an Android client, shared control-plane services, and independently authorized infrastructure. The immediate path is a private owner-controlled pilot. The existing browser proxy is an implemented starting point; native device VPN support is a separate engineering track. The broader vision remains in [PROJECT_IDEA.txt](../PROJECT_IDEA.txt), while [PROJECT_HANDOFF.md](../PROJECT_HANDOFF.md) supplies task packets and [ARCHITECTURE.md](ARCHITECTURE.md) describes the present implementation.

The current extension selects a browser proxy and obtains short-lived authorization over HTTPS. It does not create a device tunnel. Its exact control API origin bypasses the proxy; incognito, other applications, operating-system networking, and some browser-internal traffic are outside its protection boundary. Retaining proxy settings during a failure and limiting non-proxied WebRTC UDP do not prove a system-wide kill switch or complete leak protection. A local fixture demonstrates a controlled integration path, not a real country, a deployed exit, or a native VPN.

A native product needs a maintained tunnel implementation, an independently authorized endpoint, device keys, platform networking integration and tested failure controls. The existing [Node gateway](../services/gateway/index.js) forwards HTTP/HTTPS CONNECT; it is **not a WireGuard server**. Preserved Mullvad and Amnezia code supplies source material for investigation, not our operated accounts, servers, branding rights, signing authority or verified clients. Review [upstream provenance](../upstream/README.txt), [licensing](LICENSING.md) and the [archive catalog](repository/UPSTREAM_CATALOG.jsonl) before selecting inputs.

**Complete Linux first.** Audit and build one daemon/CLI target, establish a custom authorized-endpoint path, then test actual routing, DNS, IPv4/IPv6, failures and cleanup on a suitable authorized machine. Build a supported Linux application only after that proof. Keep browser acceptance moving independently when a permitted extension-capable runner exists. Android, Windows, macOS and Firefox are explicit later product destinations, not optional ideas to silently remove; each needs its own implementation and acceptance evidence. Edge, Brave and other Chromium browsers require explicit compatibility testing rather than an assumption based on engine ancestry.

Potential shared components include identity and device-authorization concepts, configuration schemas, gateway descriptions, enrollment/revocation contracts, entitlements and selected control-plane tests. The current founder-only API must be deliberately extended before it can serve native device enrollment or multiple customers. Do not assume its Basic proxy grants can become WireGuard peer keys. Tunnel adapters, privileged services/IPC, route and resolver changes, firewall/blocking behavior, secure OS key storage, installer/uninstaller behavior, signing and updates must be designed and tested separately per OS. Android additionally needs its VPN consent, background, always-on/lockdown and battery behavior established on devices.

Preserve the working extension controller/worker/popup, founder API/SQLite store, authenticated gateway and destination policy, private operations UI, local TLS fixtures, encrypted recovery, deterministic packaging, tests and source-preservation tooling. Do not rewrite them solely to adopt another framework or turn the modular single-process runtime into speculative microservices. Preserve existing source ownership and paths; keep unique native work in a deliberately selected tracked component rather than only in ignored `build/upstream/`.

The first native product should omit multi-hop, split tunneling, dedicated IP, filtering, censorship-resistance modes, enterprise/router support, billing and AI unless a later explicit scope decision justifies one. A truthful usable connection, secure configuration, revocation, tested recovery and verifiable releases take precedence. No added spending, new charging trial, public launch or store publication is authorized by this inventory. [Cost policy](COST_POLICY.md), [deployment gates](DEPLOYMENT.md) and owner decisions continue to apply.

**Defects and risks are separate.** T24 is now a reproduced dashboard defect: the audit diagnostic used the actual TLS API/Store to produce `state=exhausted`, `active=false` and rejected authorization, while real Chromium displayed one active grant and “Authorized.” Chromium reached a loopback HTTP diagnostic bridge whose upstream API requests verified TLS; this is dashboard evidence, not actual extension routing. `node /tmp/vpn-dashboard-diagnostic.mjs` exited 0 after confirming that mismatch. The temporary diagnostic is not a committed regression or an application fix. The observed defect is misleading presentation, not a demonstrated quota-enforcement bypass; the gateway/store reject exhausted authorization independently of the display. Missing real-browser acceptance, native failure controls, device secure storage and deployed recovery are unverified or missing capabilities, not proof that a particular exploit occurred. Existing historical test results remain tied to their recorded baseline; this documentation audit must identify separately any newly executed checks. No source-tree inspection establishes account-compromise resolution.

KEEP/DEFER/RECONSIDER are product recommendations, independent of implementation status and scope. Preserve historical files, tests, source archives, legal notices and working functionality regardless of classification.

## Implementation Roadmap

Priorities express dependencies and the selected first product, not unsupported dates or effort estimates. Each stage requires one bounded task/PR at a time, meaningful evidence on its final revision and [owner-controlled review](../PROJECT_HANDOFF.md). A missing external resource should remain an explicit blocker while independent useful local work continues. Scope and priority are independent: a P2 platform is a required long-term destination even while deliberately deferred from the initial MVP.

### P0 — Functional foundations

1. Preserve the validated prototype and establish actual Chrome extension acceptance through [T01](../PROJECT_HANDOFF.md#t01--real-chrome-extension-acceptance-p0-prerequisite-required). Keep managed policy intact; [T02](../PROJECT_HANDOFF.md#t02--missing-browser-failure-regressions-p1-ready) provides independent regression work while a legitimate runner is unavailable. Investigate defects using real reproductions; [T24](../PROJECT_HANDOFF.md#t24--correct-reproduced-dashboard-exhausted-grant-status-p1-ready) is a reproduced misleading dashboard display, while actual exhausted authorization was rejected. Add a committed regression and fix without claiming a security bypass.
2. Audit one Linux native target and its source/license/build inputs through [T03](../PROJECT_HANDOFF.md#t03--audit-one-native-linux-build-target-p0-ready-recommended-next-task), then reproduce its selected build in [T04](../PROJECT_HANDOFF.md#t04--reproduce-the-selected-native-build-p0-depends-on-t03). Determine which missing archive submodules/generated assets affect that target. A successful build is a prerequisite, not device VPN acceptance.
3. Define the tracked native/privilege boundary in [T05](../PROJECT_HANDOFF.md#t05--choose-and-implement-a-tracked-native-integration-boundary-p0-prerequisite-required) and independent endpoint/device-configuration contract in [T30](../PROJECT_HANDOFF.md#t30--authorized-native-endpoint-and-device-configuration-contract-p0-prerequisite-required), using [T13](../PROJECT_HANDOFF.md#t13--current-threat-model-and-data-lifecycle-p1-ready) for threat/data/key boundaries. These decisions precede platform UI expansion.
4. Resolve actual endpoint/privileged-machine needs; apply [T07](../PROJECT_HANDOFF.md#t07--private-hosting-cost-and-authorization-gate-p0-for-deployment-prerequisite-required) before obtaining hosting. Run [T06](../PROJECT_HANDOFF.md#t06--smallest-real-native-tunnel-proof-p0-prerequisite-required) for an authorized real tunnel and essential routes/DNS/IPv4/IPv6/failure/cleanup verification. Never substitute a loopback fixture, binary or archive for this gate.
5. Correct any demonstrated security defect in existing functionality promptly, retaining restrictive auth/destination/privacy controls and negative regressions. Run relevant supply-chain checks under [T14](../PROJECT_HANDOFF.md#t14--ongoing-dependency-and-source-supply-chain-review-p1-ready); do not weaken verification to unblock builds.

### P3 — Optional enhancements

Consider one justified [T21](../PROJECT_HANDOFF.md#t21--advanced-protection-features-p3-optional-product-decisions) capability at a time: multi-hop, split tunneling, dedicated IP, filtering, censorship resistance, advanced location selection, enterprise or router support.
